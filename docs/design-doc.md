## 2. Принципы

Из [PRODUCT.md → Product Principles](../PRODUCT.md#product-principles):

1. **Решённая задача, а не «сайт»** — подача проблема → решение → результат.
2. **Технологии внутри истории** — админка, интеграции, SEO показаны в работе, а не отдельными блоками-каталогами.
3. **Только честные доказательства** — реальные кейсы, отзывы, сроки; нет данных → видимая заглушка, а не выдумка.
4. **Вход без трения** — квиз и живой менеджер вместо ТЗ и созвонов для нетехнического владельца.
5. **Скорость как доказательство** — сайт сам подтверждает обещание: быстрая загрузка, точная работа.

## 5. Компоненты UI (реестр)

Реестр — 15 позиций. Вместо типовых e-commerce-компонентов из общего брифа CLAUDE.md («карточка товара», «фильтры», «бейджи скидок») их роль здесь выполняют карточка кейса, чипы квиза и плашки офферов — это зафиксированное бизнес-решение: сайт продаёт услугу студии, а не товары ([PRODUCT.md → Capabilities and Constraints](../PRODUCT.md#capabilities-and-constraints)).

| Компонент | Назначение | Состояния | Доступность |
|---|---|---|---|
| Шапка (десктоп/мобильная) | Десктоп: логотип, якоря, «Стать партнёром», тема, CTA «Обсудить проект». Мобильная: логотип, CTA, бургер (раскрывает «Мобильное меню») | default · pinned/scrolled (способ решает этап 4) · открытое мобильное меню | `<header>/<nav>`, видимый порядок фокуса, логотип — ссылка «наверх» с доступным именем, бургер с `aria-expanded`/`aria-controls` |
| Мобильное меню | Полноэкранная навигация: якоря, «Стать партнёром», тема, Telegram | closed · open | `role="dialog"`/`aria-modal`, фокус-ловушка, закрытие по Esc / клику по пункту / кнопкой, фокус возвращается на бургер |
| Переключатель темы | Смена светлая/тёмная поверх системной | default · hover · focus · pressed (текущая тема) | доступное имя текущего состояния; без JS переключения нет — тема берётся из `prefers-color-scheme` |

| Аккордеон FAQ (details/summary) | 8 вопросов, ответы по фактам брифа | closed (default) · open · focus · hover | нативные `<details>/<summary>` — работают без JS и с клавиатуры; анимация раскрытия — прогрессивное улучшение поверх рабочей базы |

| «Пустая ячейка» — заглушка | Видимый маркер незаполненных данных: `[задача]`, `[результат]`, `[цена]`, `[текст политики]` | default (видна всегда, пока не заменена реальным текстом) | часть обычного текстового потока, не `aria-hidden` — заглушку видят все пользователи одинаково, включая скринридер |
| Плашки офферов | «Бесплатный макет за 24 часа», «Скидка 60% клиентам СДЭК» | default | текст, не картинка; соседний CTA несёт свои стандартные состояния |

## 6. Направление

Выбор направления — раунд `/impeccable` этапа 4 (см. [PLAN.md](./PLAN.md)), не часть этого документа: полный контракт — [.impeccable/surfaces/site-src-app-page-tsx.md](../.impeccable/surfaces/site-src-app-page-tsx.md). **Контракт не копируется в код сайта** — реализация и `03-design-system.md` только ссылаются на него.

**THESIS.** Канон сайта e-commerce-студии на уровне референсов брифа (Uncap, Newthink, Makro, Intaro, AGIMA): понятный продукт → доказательства → действие. Без дешёвой версии канона — счётчиков, эмодзи, одинаковых карточек-иконок как структуры страницы, неона и частиц.

**OWN-WORLD.** Палитра greenboxweb.ru 1:1 (§7.1), поля по бокам 100 px на десктопе (уточнение заказчика), панели со скруглением 16–24 px, кнопки-пилюли, мягкие тени со смещением. Ноутбук и телефон на первом экране — интерфейсы витрины и админки, собранные в коде, а не скриншоты.

**Первый экран.** Тёмная сцена `#0A0A14` с фоновым изображением под затемнением (кандидатов подбирает студия, выбирает заказчик — §1). Слева заголовок «Интернет-магазины под ключ» (Martian Grotesk wide, «Интернет-магазины» в единственном на сайте зелёно-циановом градиенте), подзаголовок, CTA — как в §3.1 (Hero). Справа ноутбук с витриной и телефон с админкой, шапка поверх сцены.

**Фирменное взаимодействие.** Переключатели админки на телефоне вживую меняют витрину на ноутбуке — продукт студии показан в работе, а не описан текстом.

**Движение.** Шаблонного всплытия блоков нет; движутся 8 авторских моментов (вход первого экрана, «инспектор» фона, автопроход переключателей, линейки «Что вы получаете», шкала процесса, лента кейсов, FAQ, шаги квиза) на `cubic-bezier(0.16,1,0.3,1)`, каскад 70 ms, ховеры 0.25 s. Кейсы на десктопе — закреплённая секция с горизонтальной прокруткой (§8 «Кейсы»). Везде — `prefers-reduced-motion` и работа без JS.

## 8. Логика поведения

**Тема.** По умолчанию — системная (`prefers-color-scheme`); ручной выбор запоминается в `localStorage`; тема ставится до отрисовки — мигания нет.

**Навигация и якоря.** Плавный скролл к якорю с учётом высоты шапки, отключается при `prefers-reduced-motion`. Шапка всегда на месте: над первым экраном прозрачна, после прокрутки плотная (`03-design-system.md` §6).

**Мобильное меню.** Полноэкранное; закрывается по Esc, клику на пункт или кнопкой закрытия; фокус заперт внутри меню на время открытия.

**Квиз.** Виден номер шага («Шаг N из 5», тег `.step N / 5`). Шаги 1–5 можно пропускать: в каждом есть вариант «не знаю», «Далее» без выбора разрешено. Есть «Назад»; ссылка «Сразу оставить контакты» ведёт на шаг 6. Переход между шагами анимирован, фокус переходит на заголовок нового шага — скринридер объявляет его. Отправка проходит состояния: ожидание → ошибки полей (текстом рядом с полем, не только цветом) → отправка (кнопка заблокирована, показан индикатор) → успех («Заявка отправлена. Мы свяжемся с вами», ответы остаются видны) → ошибка сервера (сообщение, «Попробовать ещё раз», запасной путь — Telegram @infogreenbox).

**Формы.** Валидация рядом с полем, не только цветом. Согласие обязательно: без галочки отправка блокируется, пояснение — рядом. Работают без JS: обычный POST, ответ страницей; JS — прогрессивное улучшение, заявка не теряется без него.

Контракт `POST /api/lead` (реализация: `site/src/lib/lead/lead.ts`, `site/src/app/api/lead/route.ts` — только чтение):

- **Поля.** `source` (`quiz`|`contact`) · `name`* (≤100 симв.) · `contact`* («телефон, Telegram или email», 3–200 симв.) · `comment` (≤2000 симв., многострочный) · `consent`* (чекбокс) · `answers.<business|siteType|features|integrations|volume>` (видимый текст вариантов, до 15 значений по 100 симв.) · `answers.sdekContract` · `offer` (`mockup`|`sdek` — по кнопке какого оффера пришли; остальное отбрасывается) · `channel` (`phone`|`telegram`|`email` — переключатель способа связи; сервер проверяет формат и, если выбран не тот способ, определяет верный по значению — `resolveChannel`; в Telegram «Контакт: … (телефон)») · `page` (путь отправки, начинается с `/`, иначе отбрасывается; ≤200 симв.) · `website` — honeypot, должен остаться пустым.
- **Коды ответа.** `200` успех (в т.ч. тихий приём при honeypot — бот не должен понять, что его поймали) · `400` битый JSON или ошибка полей (тело называет коды полей) · `413` тело больше 16 КБ · `415` не JSON/urlencoded/multipart · `429` превышен лимит частоты · `502` Telegram не принял, заявка всё равно ушла в лог.
- **Без JS.** Ответ — не JSON, а `303` редирект на `/?lead=ok|error#contact` (`#quiz`, если `source=quiz`); при ошибке конкретных полей (400) добавляется `field=` — их коды через запятую (`source`, `name`, `contact`, `comment`, `consent`).
- **Honeypot.** Заполненное поле `website` — заявка не уходит, но ответ как у успеха (200 / редирект `lead=ok`), чтобы не выдавать защиту боту.
- **Частота.** Не больше 5 заявок с одного IP за 10 минут и 60 в минуту суммарно; IP берётся из `X-Forwarded-For`/`X-Real-IP`. Лимит живёт в памяти процесса — при нескольких инстансах нужен внешний счётчик (Redis, `limit_req` nginx).

Токен бота — только на сервере, в клиентский код не попадает.

**Кейсы.** Десктоп — закреплённая секция с горизонтальным движением по скроллу. Фокус с клавиатуры на ссылке карточки вне экрана прокручивает страницу так, чтобы карточка стала видна. При `prefers-reduced-motion` — обычная вертикальная сетка вместо горизонтального движения. Мобильная раскладка — лента со scroll-snap (карточка на ширину экрана минус поле, край следующей виден); от 1024 px без JS и при reduced-motion — сетка: лидер + 2×2. Счётчик `.case 01 / 05`.

**FAQ.** Нативные `details/summary` — открытие и закрытие работают без JS и с клавиатуры; анимация раскрытия — прогрессивное улучшение поверх рабочей базы.

**Движение.** Три режима: полное, уменьшенное (`prefers-reduced-motion`), без JS. Во всех — весь контент виден сразу: анимация не может быть условием доступа к содержанию.

Полный список состояний к проектированию: [02-ux-structure.md → 8. Состояния](./02-ux-structure.md#8-состояния-которые-нужно-спроектировать).
