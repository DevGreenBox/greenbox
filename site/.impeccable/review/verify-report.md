# Проверка невидимой части чеклиста — «ЗелёнаяКоробка»

29.09.2026. Проверяли продакшен-сборку Next.js 16.2.10 standalone на `http://localhost:3100`. Сервер запускал координатор, в ходе проверки его не перезапускали и не пересобирали. Код не менялся.

Инструменты:
- Lighthouse 13.5.0, Chromium 151, `--headless=new`;
- axe-core 4.13.0: теги `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`; `best-practice` учитывался отдельно;
- playwright-core 1.62.1: Chromium 151 (chromium-1244) и WebKit 26.5 (webkit-2336).

Контейнер: 4 vCPU, 8 ГБ, сайт на localhost. Сеть и CPU в Lighthouse симулируются.

Сырые данные и скрипты лежат в `.impeccable/review/verify/`, перечень — в конце отчёта.

## Дефекты

### Блокер

**1. На мобильном LCP 3,7 с, а чеклист требует загрузки быстрее 2 с.**
- Где: `/`, элемент LCP — подзаголовок первого экрана `section#top > div.wrap > div > p.mt-(--space-lead)`.
- Как воспроизвести: `CHROME_PATH=… lighthouse http://localhost:3100/ --chrome-flags="--headless=new --no-sandbox"` (мобильный профиль по умолчанию). Получается LCP 3,65–3,74 с и Performance 83–86. PageSpeed Insights после выката считает так же и покажет эту цифру заказчику.
- Что показали отдельные прогоны:
  - без JS LCP 2,6 с (−1,15 с);
  - без шрифтов 3,0 с (−0,6 с);
  - без анимации входа и без JetBrains Mono — без изменений.
- При реальном троттлинге с теми же параметрами LCP 1,5–2,15 с, анимация входа добавляет к нему 0,2–0,85 с (с reduced-motion 1,3 с).
- Куда смотреть: меньше JS до первой отрисовки (гидратация, 13 КБ legacy-полифилов, 28 КБ неиспользуемого), лёгкие шрифты первого экрана (Unbounded 94 КБ + Onest 50 КБ), 2 блокирующих CSS (оценка −400 мс).

### Важно

**2. WebKit падает при прокрутке главной из-за `filter: blur(6px)` в появлении `data-reveal="soft"`.**
- Где: `src/styles/base.css`, правило `.reveal-on [data-reveal='soft']:not([data-revealed])`. Затронуты квиз (`Quiz.tsx`), отзывы (`Reviews.tsx`) и «Почему мы» (`Why.tsx`).
- Как воспроизвести: `node verify/webkit-crash.mjs`. На `/` вкладка падает («Target crashed») в 7 из 10 прогонов, в разных местах: process, team, faq, иногда сразу после загрузки. `/privacy` — 0 из 3.
- Бисекция, по 5 прогонов на 390 (`verify/webkit-bisect.mjs`):

  | Режим | Падений |
  |---|---|
  | как есть | 5 из 5 |
  | reduced-motion | 0 |
  | без JS | 0 |
  | `*{filter:none}` | 0 |
  | `[data-reveal]{filter:none}` | 0 |
  | `mask-image:none` | 4 из 5 |
  | `#hero-title{filter:none}` | 4 из 5 |
  | синтетическая длинная страница | 0 |

- Оговорка: это сборка WebKit для Linux с программной отрисовкой. На реальном iPhone не проверено. Проверить на устройстве; если падение подтвердится, это блокер. Размытие больших блоков тяжело для памяти и в iOS Safari.

**3. Ссылки внутри текста не отличаются от текста.**
- axe `link-in-text-block` (WCAG 1.4.1, уровень A): ссылка «персональных данных» в согласии.
  - Финальная форма: `#contact .check__label a[href="/privacy"]` (в axe `a[aria-describedby="_R_dd5flb_"]`), #E8E8F0 на тексте #A0A0B8 — 2,09:1.
  - Квиз: `#quiz .check__label a[href="/privacy"]` (в axe `a[aria-describedby="_R_kkh5flb_"]`), #1A1A2E на #4A4A68 — 2,0:1 в светлой теме, 2,09:1 в тёмной.
  - Подчёркивания нет, а нужно ≥ 3:1 к тексту или подчёркивание.
- Та же причина там, где axe не срабатывает:
  - `/lead/sent`: «@infogreenbox» внутри абзаца — цвет как у текста, без подчёркивания (кадр `verify/forms/nojs-sent.png`);
  - `/privacy`: e-mail и Telegram в реквизитах.
- Причина: в собранном CSS оба правила лежат в `@layer base`.
  - Preflight Tailwind `a{color:inherit;text-decoration:inherit}` имеет специфичность 0,0,1.
  - Правило `:where(a:not([class])),.link{text-decoration-line:underline…}` из `base.css` за счёт `:where()` имеет 0,0,0 и проигрывает.
  - Поэтому подчёркивание есть только у ссылок с классом `.link`. Вычисленный `text-decoration-line` у `.check__label a` равен `none` (`verify/cases/results.json`).

**4. На телефоне фокус на «Открыть сайт» в чётных кейсах остаётся за краем экрана.**
- Где: 390, Chromium и WebKit, лента `#cases [data-viewport]` (`scroll-snap-type: x mandatory`).
- Как воспроизвести: клик по «Кейсы», затем Tab на ссылку карточки 1, ещё Tab. Ссылка `#cases [data-item]:nth-child(2) a.btn--text` стоит на 362–495 px при ширине экрана 390, видно 28 px. `scrollLeft` ленты 0, счётчик «01 / 08». Следующий Tab сразу перебрасывает ленту на карточку 3 (`scrollLeft` 684). С карточками 4, 6 и 8 то же. Кадр: `verify/cases/chromium-390-tab2.png`.
- Вероятная причина: браузер докручивает ленту до ссылки, а mandatory-snap возвращает её к ближайшей точке, то есть к карточке 1.
- На 768 и на десктопе всё в порядке.

**5. Нет картинки для превью ссылок.**
- `og:image` и `twitter:image` отсутствуют, хотя `twitter:card` = `summary_large_image`.
- Ссылка на сайт в Telegram, VK и WhatsApp будет без картинки.
- Где: `src/app/layout.tsx`, поля `metadata.openGraph` и `metadata.twitter`. Файла `opengraph-image` нет.

**6. Lighthouse Accessibility 97 из-за декоративных подписей «чертежа» на первом экране.**
- Где: `.GridBackdrop-module__…__lbl`, подписи «<header>», «<section class="hero">», «.product-card». Цвет #6A6A80 на #0A0A14 даёт 3,73:1 при 11 px, нужно 4,5:1.
- Слой под `aria-hidden`, и по WCAG 1.4.3 декоративный текст исключён. Но axe и Lighthouse засчитывают это как нарушение контраста. Других причин для 97 вместо 100 нет, и именно это заказчик увидит в отчёте. Цвет #8888A0 дал бы 5,7:1.

## Методика: кратко

- **Lighthouse.** Сначала 3 мобильных прогона и 3 десктопных по `/`, затем по одному a11y-, SEO- и best-practices-прогону для `/privacy`, `/lead/sent` и `/lead/error`. Медианы взяты по каждой метрике отдельно. В первом мобильном прогоне Lighthouse предупредил о медленном CPU (benchmarkIndex 966). В остальных benchmarkIndex 1244–1399, предупреждений нет. Отдельные прогоны: reduced-motion (`--force-prefers-reduced-motion`) и блокировка `*.js`, `*.woff2`, JetBrains Mono.
- **axe.** Перед замером страница прокручивалась до низа, чтобы все появления дошли до `data-revealed="done"`. Отдельно проверены состояния, которых нет при загрузке.
- **Видимость фокуса.** Проверялась по кадрам: пиксели с фокусом против тех же пикселей после `blur()`. Считались число изменившихся пикселей и контраст между состояниями.
- **Без JS.** Кадры и отправка форм — с настоящим `javaScriptEnabled:false`, только клавиатурой и сетью. Инструменты Playwright, которым нужен JS в странице, в этом режиме зависают. Поэтому замеры видимости делались на странице с вырезанными `<script>`.
- **WebKit.** Строки таблицы для WebKit сняты с обходом `[data-reveal]{filter:none}` (переменная `WK_NOBLUR=1`). Без обхода в тех же прогонах WebKit падал (дефект 2).
